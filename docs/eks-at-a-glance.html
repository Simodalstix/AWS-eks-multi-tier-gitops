Say it in 30 seconds

"I built an EKS platform on AWS to learn what a platform support engineer looks after. Terraform builds the network, the cluster and the worker VMs. The apps run as containers on those VMs, and Kubernetes keeps them running. Argo CD deploys whatever is in Git. Prometheus and Grafana tell me when something is wrong. It is a lab, not production, and I tear it down after each session to keep the cost low."

What is actually what

One rule ties it together: everything talks to the API server, and only the API server talks to etcd. The parts never call each other to coordinate. Each one watches the API server for its kind of work, does it, and writes the result back. The other lines in the picture are real traffic: user requests, metrics, name lookups, and calls out to AWS and GitHub.

Under the hood: what a container really is

A process on the node, started by containerd. The kernel gives it its own view with namespaces (its own process list, network, filesystem) and caps its CPU and memory with cgroups. Its files come from the image layers, stacked with overlayfs.

No second kernel: every container on a node shares the node's Linux kernel. That is the difference from a VM, and why containers start in seconds.

On the node, the app shows up in an ordinary process list: ps aux | grep nginx. Containers: sudo crictl ps.

Under the hood: the control plane is VMs too, just not yours

Per AWS docs: each cluster gets its own control plane, with at least two API server instances and three etcd instances spread over three Availability Zones, in an AWS-owned account. AWS patches, scales and replaces them.

You never see those VMs. You see one HTTPS endpoint. In this project it is reachable from the internet, so kubectl works from your laptop.

Under the hood: how a pod gets an IP

The VPC CNI plugin gives each pod a real IP from the VPC, attached as an extra address on the node's network card (ENI). So pods are directly reachable inside the VPC, and the ALB can send traffic straight to them.

Containers in the same pod share one network namespace: one IP, and they reach each other on localhost.

Under the hood: what runs on the node itself

kubelet and containerd are systemd services, like Docker engine on a plain VM. kubelet asks the API server what should run on this node, then tells containerd to run it.

Get on the node with SSM Session Manager (no SSH key needed), then systemctl status kubelet and journalctl -u kubelet.

Managed node group vs Fargate. This project uses a managed node group: the worker VMs are your EC2 instances, and AWS helps by creating, upgrading and draining them. With Fargate there are no nodes for you at all: AWS runs each pod on a VM you never see, and you pay per pod. Less to look after, less control: no logging in to a node, no DaemonSets. This project does not use Fargate.

Under the hood: how Terraform turns into EC2 instances

Terraform (infrastructure/eks.tf) asks EKS for a managed node group: t3.medium, Spot, Amazon Linux 2023, minimum 1, normally 2, maximum 4.

EKS then creates an Auto Scaling Group and a launch template in your account. The Auto Scaling Group launches the EC2 instances. When a node boots, its kubelet registers with the API server and it becomes a node.

Under each instance is AWS hardware running AWS's hypervisor (Nitro). That layer is the same for every EC2 instance and is never visible to you.

Under the hood: the numbers and the triggers

Pod autoscaler maths. Each pod asks for 100m (0.1 CPU). The target is 80% of that, so 80m on average. It needs metrics-server, installed by setup-argocd.sh; without it the HPA shows <unknown> and does nothing. Rule: new count = current count x actual / target, rounded up. 2 pods averaging 160m: 2 x 160 / 80 = 4 pods.

The scheduler uses what pods ask for, not what they use. A VM is "full" when the requests add up to its capacity, even if real CPU is low. A t3.medium has 2 CPUs and 4 GiB, minus what the system keeps back. With the default VPC CNI, a t3.medium also holds at most 17 pods (AWS published limit; not checked on this cluster), and that can run out before CPU does.

Why Terraform does not undo the autoscaler. The Cluster Autoscaler changes the Auto Scaling Group's desired count. The EKS Terraform module ignores changes to that number (ignore_changes = [scaling_config[0].desired_size]), so a later terraform apply leaves it alone. Terraform only owns the min and max.

How the Cluster Autoscaler finds the VMs. It looks for the Auto Scaling Group tagged k8s.io/cluster-autoscaler/enabled and k8s.io/cluster-autoscaler/eks-portfolio-dev, set in infrastructure/eks.tf, and uses its own IAM role to change the count.

Timing (upstream defaults, not tuned in this repo): the HPA checks about every 15 seconds and waits 5 minutes before scaling down. The Cluster Autoscaler checks about every 10 seconds and removes a VM that has been underused for about 10 minutes. A new EC2 node takes a few minutes to be ready.

What can go wrong. At 4 VMs the Cluster Autoscaler stops, and extra pods stay Pending. Spot with one instance type: if AWS has no spare t3.medium Spot capacity, the new VM may not arrive. Honest lab note: 10 app pods ask for 1 CPU in total, so a third VM is only needed if the other pods (Argo CD, monitoring) already take most of the room.

The three arrows

1 A request

  1. User hits the load balancer's address.
  2. The ALB sends it straight to a healthy frontend pod's IP. The LB controller keeps that list current.
  3. nginx in the container answers.
  4. If the app looks up another service by name, CoreDNS answers with its IP.

No control plane in this path. If the API server went away, traffic would keep flowing; only changes would stop.

2 A deploy

  1. You merge a change in Git.
  2. Argo CD sees Git differs and sends the new version to the API server, which stores it in etcd.
  3. The controller manager sees it and creates new pod records.
  4. The scheduler gives each new pod a node.
  5. That node's kubelet sees it; containerd pulls the image and starts it.
  6. Once it is healthy, the ALB starts sending it traffic and an old pod is removed.

Every step goes through the API server. Rollback is a Git revert.

3 A build

  1. From your laptop, Terraform creates the VPC, the control plane, the node group and IAM roles.
  2. The node VMs boot and their kubelets register with the API server. EKS adds CoreDNS and the pod networking itself.
  3. From your laptop, the setup script uses kubectl and helm to install Argo CD, the LB controller, metrics-server and the Cluster Autoscaler.
  4. Argo CD deploys the app and the monitoring stack from Git.

All of it is code, so it is torn down and rebuilt each session.

Under the hood: how the parts talk

Kubernetes is a database of what should be running (etcd) behind an API (the API server). Everything else is a loop that watches it and fixes reality: the scheduler assigns pods to nodes, controllers keep the right number of pods, each node's kubelet runs what is assigned to it.

Nothing talks to the nodes directly to deploy. Argo CD writes to the API server; kubelets read from it.

Watching, not polling. Each component keeps a connection open to the API server and is told the moment something it cares about changes. That is why one change ripples through controller, scheduler and kubelet in seconds.

Who is allowed. Every caller proves who it is. You, through your AWS identity (an EKS access entry; the cluster creator is admin). Nodes, through the node IAM role. Pods, through their service account token.

A Service gives a set of pods one stable name and address (kube-proxy turns it into iptables rules on each node). In this project the ALB skips that and goes to pod IPs; the Service just keeps the list of healthy pods up to date.

When it breaks

  1. Impact first. Who is affected, how badly, since when.
  2. Stabilise. If something just changed, roll it back. Find the cause once users are OK.
  3. Follow arrow 1 inward. Load balancer, pod, container, node, AWS. The first broken box is the problem; everything after it is a symptom.
  4. Ask what changed. A deploy, a config, a scale event, an AWS event.
  5. Talk as you go, then close it: cause, fix, and one thing that stops it happening again.

If they ask for commands or a script

Know what each one is for. Nobody expects flags from memory.

The eight commands that cover most of it 
kubectl get pods -A                     # what is running, everywhere
kubectl describe pod <pod>              # why it is not: events at the bottom
kubectl logs <pod> --previous           # what the crashed container printed
kubectl get events -A --sort-by=.lastTimestamp   # what happened recently
kubectl get nodes                       # are the VMs healthy
kubectl top pods                        # CPU and memory use
kubectl rollout status deployment/<name> # is the deploy finishing
kubectl rollout undo deployment/<name>   # go back one version
A simple health-check script 
#!/usr/bin/env bash
# Quick cluster health check: nodes, unhealthy pods, recent warnings.
set -euo pipefail

echo "== Nodes"
kubectl get nodes

echo "== Pods not Running or Completed"
kubectl get pods -A --no-headers | awk '$4 != "Running" && $4 != "Completed"'

echo "== Last 10 warnings"
kubectl get events -A --field-selector type=Warning --sort-by=.lastTimestamp | tail -n 10

Explain it in one line: "Is the hardware OK, is anything not running, and what has the cluster complained about lately." Known gap: a pod can be Running but not Ready; kubectl get pods shows that in the READY column.
