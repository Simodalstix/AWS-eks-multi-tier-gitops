EKS playbook

Build it, watch each part appear, break it on purpose, tear it down. Every stage says what to run, what to watch, and what it proves. Region ap-southeast-2, cluster eks-portfolio-dev, commands from the repo root. The full checklist with every expected line is docs/live-session.md; this page is the map.

Set up three terminals

1 Do

Runs the scripts and the drill commands. Log everything for the write-ups:

mkdir -p ~/eks-sessions
script -f -a ~/eks-sessions/$(date +%F).log

exit at the end closes the log.

2 Watch

Read-only. Changes nothing, so leave it running all session:

watch -n 5 scripts/look.sh all

Swap in a narrower view per stage: aws, nodes, app, argo, system, irsa, alerts, events.

3 User

From stage C, once the ALB exists. What a user would see, every 2 seconds:

ALB=$(kubectl -n portfolio-apps get ingress frontend -o jsonpath='{.status.loadBalancer.ingress[0].hostname}')
while true; do printf '%s %s\n' "$(date -u +%T)" "$(curl -s -o /dev/null -m 3 -w '%{http_code}' -H 'Host: frontend.local' "http://$ALB/")"; sleep 2; done

0 Check: start from an empty region

Run 
aws --version; terraform version; helm version; kubectl version --client
session-manager-plugin --version; jq --version
aws sts get-caller-identity
aws eks list-clusters --region ap-southeast-2
aws ec2 describe-nat-gateways --region ap-southeast-2 --filter Name=state,Values=pending,available --query 'NatGateways[].NatGatewayId'
aws elbv2 describe-load-balancers --region ap-southeast-2 --query 'LoadBalancers[].LoadBalancerName'
What it proves

You are the identity you think you are, and the region is clean, so everything you see later was made tonight.

Done when

The three lists are empty. kubectl client 1.35 or 1.36: it supports one minor version either side of the 1.35 server (yours was v1.37.1 on 2026-10-18).

A Plan: Terraform says what it will build

Before this

you run Push the branch. Argo CD deploys from GitHub HEAD, not your working tree; setup-argocd.sh warns if they differ.

Run 
scripts/deploy-infrastructure.sh

Runs terraform init, validate, plan, prints the Plan: line, then stops at Apply this plan? (y/N).

What it proves

Terraform builds the AWS layer only. The plan has no Auto Scaling Group and no load balancer: EKS makes the first, the LB controller the second. Nothing inside Kubernetes is in it.

Done when

Plan: 84 to add, 0 to change, 0 to destroy. Anything to change or destroy: answer N and stop. Your local state is not what you think.

B Apply: the network, the control plane and the nodes

Run

you run Answer y at the prompt. The script then backs up the state to ~/tfstate-backups/, runs aws eks update-kubeconfig and kubectl get nodes -o wide, and prints how long the apply took.

Watch 
watch -n 20 scripts/look.sh aws

Works before kubectl is configured. Cluster CREATING then ACTIVE. Then the ASG appears with desired 2 and two instances go InService. Once the script has configured kubectl: scripts/look.sh nodes.

What it proves

The chain from the glance page: node group (Terraform) to Auto Scaling Group (EKS) to EC2 instances to registered nodes. Each instance id in look.sh aws matches one node in look.sh nodes.

Done when

2 nodes Ready, capacity type SPOT, Amazon Linux 2023, kubelet v1.35.x. Costs are running from here.

C Bootstrap: controllers, Argo CD, then the apps

Run 
scripts/setup-argocd.sh

Installs Argo CD v3.5.5, the two IRSA service accounts, the LB controller, metrics-server and the Cluster Autoscaler, creates the Grafana secret, then applies the Argo CD project and the frontend and monitoring Applications. It refuses to run if kubectl points at another cluster.

Watch

look.sh all in terminal 2. Then scripts/look.sh argo for Synced and Healthy, and scripts/look.sh app until the Ingress has an ALB hostname and the targets are healthy. Then start terminal 3.

What it proves

Two ways in through the same API server. kubectl and helm push the layer Argo CD needs. Argo CD then pulls the rest from Git. Nothing outside the cluster deploys the apps.

Done when

The script prints the Argo CD password and the Grafana lines. Both Applications Synced and Healthy. Terminal 3 shows 200. Save the non-empty output of the positive-control commands in checklist step C: teardown proves emptiness against it.

D Verify: what only a live cluster can show

D1 IRSA

Pods get their own AWS role from the service account annotation.

scripts/look.sh irsa

Done: both service accounts show a role ARN, both controller pods show AWS_ROLE_ARN, frontend shows nothing.

D2 LB controller

An Ingress becomes a real ALB with pod IPs as targets.

scripts/look.sh app

Done: 200, one target per frontend pod, all healthy.

D3 Cluster Autoscaler

Pods that do not fit make the ASG grow; empty nodes make it shrink.

kubectl create namespace ca-drill
kubectl -n ca-drill create deployment ca-drill --image=registry.k8s.io/pause:3.10 --replicas=6
kubectl -n ca-drill set resources deployment ca-drill --requests=cpu=500m,memory=128Mi
watch -n 10 scripts/look.sh nodes    # terminal 2
kubectl delete namespace ca-drill    # then wait for scale-down

Done: Pending pods, desired count rises (max 4), new nodes Ready. After the delete, back down within about 20 to 30 minutes, never below 1.

D4 to D6 the rest
  • HPA: look.sh app shows cpu: N%/80%, not <unknown>.
  • SSM: aws ssm start-session --region ap-southeast-2 --target <instance-id> opens a shell on a node, no SSH key.
  • Alerts: look.sh alerts lists only Watchdog firing.
  • Grafana: kubectl -n monitoring port-forward svc/monitoring-grafana 3000:80, password from the secret.

All of D is unverified: written from the repo and docs, never run against a cluster. The service-proxy path that look.sh alerts uses (prometheus-prometheus:9090) is unverified too; the checklist's port-forward in D6 is the fallback.

F Drills: break it, watch it, fix it

The loop, for every drill 
scripts/drill.sh break <drill>      # note the time it prints
# triage by hand: the checklist has the commands per drill
scripts/drill.sh restore <drill>    # even if you already fixed it

Record the break time, when you first saw the symptom, what terminal 3 showed, and anything that did not match. Then write a runbook from the log: cp runbooks/_template.md runbooks/<slug>.md.

What the drills prove together

Where a failure sits decides who notices. Most faults hit the new pod of a rollout, and the old pods keep serving. One fault in the Service record takes everyone down while every pod looks fine.

G Teardown: the ALB first, then everything Terraform made

Run 
scripts/teardown.sh
  1. Deletes the Argo CD Applications. Their finalizer deletes the Ingress, and the LB controller deletes the ALB, target groups and k8s- security groups.
  2. Waits up to 5 minutes for those to go. Stops if they do not.
  3. Stops if either ECR repository has images.
  4. you run terraform destroy, which asks for confirmation.
  5. Prints the proof: every line empty, state entries 0.
Watch 
watch -n 20 scripts/look.sh aws

The k8s- load balancer disappears first. Then the cluster goes DELETING, then the commands start to error because it is gone.

If a drill is still broken

Restore it first, especially drill 8: with IRSA broken the controller cannot delete the ALB, and destroy then hangs on the VPC. Cluster already unreachable: scripts/teardown.sh --skip-cluster.

Done when

Proof lines empty where step C's positive control was not. Check again the next day: KMS key pending deletion (7-day window), a log group EKS may recreate, NAT data and LCUs billed after the fact.
